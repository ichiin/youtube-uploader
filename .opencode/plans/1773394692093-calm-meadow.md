# Test Script: Upload 4 Videos in Batches of 2

## Goal

Create a visual test script that uploads 4 dummy videos to YouTube in batches of 2 (concurrent), with a random 6-character playlist name. This mimics the replays-upload watcher.js flow and helps debug re-upload issues.

## Re-Upload Bug Root Cause (for reference)

The replays-upload `watcher.js` re-uploads videos because:

1. **No persistent upload tracking** -- the `processing` Set is in-memory only (line 51). On container restart, it's lost.
2. **Startup scan re-queues all stable files** (lines 674-685) without checking if they were already uploaded.
3. **Trios files stay on disk** through the long analysis pipeline -- if the container restarts mid-analysis, the already-uploaded file gets re-queued.
4. **Null YouTube ID skips cleanup** (line 525-530) -- if IPC fails, the file isn't deleted and gets re-uploaded next scan.

Fix: Add persistent tracking (e.g., a `.uploaded` marker file or local JSON log) checked before starting the pipeline.

## Files to Create

### 1. `test.js` -- Main orchestrator

-   Location: `/home/takky/dev/youtube-uploader/test.js`
-   Generates 4 test videos via ffmpeg
-   Manages a SlotPool(2) for concurrency
-   Spawns `test-worker.js` as child processes (one per video)
-   Communicates via Node.js IPC (like replays-upload's `uploadToYoutube()`)
-   Colorful console logging with timestamps, slot IDs, progress
-   Prints summary table on completion

### 2. `test-worker.js` -- Upload subprocess

-   Location: `/home/takky/dev/youtube-uploader/test-worker.js`
-   Receives video config via `process.env.VIDEO` (JSON)
-   Calls `upload(credentials, [video], puppeteerOptions, messageTransport)`
-   Sends YouTube URL back via IPC: `process.send({ type: "youtube_id", youtubeId })`
-   Isolated process = isolated module-level `page`/`browser` variables (avoids the concurrency bug in upload.ts:71-72)

### 3. `.env` -- Credentials (user must fill in)

-   `YT_EMAIL` and `YT_PASSWORD`

## Implementation Details

### Video Generation (ffmpeg)

-   4 videos, each 10 seconds, 1280x720, libx264 ultrafast
-   Different background colors (blue, pink, green, orange) with text overlay ("Test Video 1" etc.)
-   Silent audio track (YouTube requires it)
-   Stored in `test-videos/` directory

### Cookie Setup

-   Copy cookies from `../replays-upload/yt-auth/cookies-takkynaraka-gmail_com.json` to `./yt-auth/`
-   Cookie path derived from email: `cookies-{user}-{domain}.json` (dots -> underscores)
-   No `userDataDir` (would disable cookie store per upload.ts:63)

### Concurrency Model (matching watcher.js)

```
SlotPool(size=2)
  .acquire() -> returns slot index (0 or 1)
  .release(slot) -> frees slot for next waiter

Flow with 4 videos:
  t=0: video1 -> slot-0 (spawn worker), video2 -> slot-1 (spawn worker)
  t=X: first to finish releases slot -> video3 acquires it
  t=Y: next to finish releases slot -> video4 acquires it
  t=Z: all done -> print summary
```

Each slot spawns a separate `node test-worker.js` child process, receiving video config via env and returning YouTube ID via IPC.

### Error Handling

-   Each worker is independently try/caught -- one failure doesn't abort others
-   Slot released in `finally` block (no pool deadlock)
-   Worker exit code != 0 treated as failure
-   IPC timeout fallback (30s after process close) in case message is lost
-   Fatal errors (no .env, no ffmpeg) exit early

### Cleanup

-   Test videos deleted after all uploads complete
-   `--keep` flag to preserve them for debugging
-   `yt-auth/` directory left intact (reusable cookies)

## Usage

```bash
# 1. Create .env with credentials
echo "YT_EMAIL=your_email@gmail.com" > .env
echo "YT_PASSWORD=your_password" >> .env

# 2. Run (requires display for Chrome -- run on desktop or with Xvfb)
node test.js

# 3. Keep test videos after upload
node test.js --keep
```
